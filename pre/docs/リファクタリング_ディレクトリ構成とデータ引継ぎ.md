# リファクタリング時のディレクトリ構成とデータ引継ぎ

**目的**: リファクタ前のコードを `pre/` に退避し、**改編後のコードはおおもとのディレクトリ（ルート）に格納**する構成にする。あわせて既存データ（DB・画像）の引継ぎ方法を記載する。

---

## 1. ディレクトリ構成（可能です）

### 1.1 方針

| 場所 | 内容 |
|------|------|
| **pre/** | リファクタ**前**のコード一式（バックアップ・参照用）。実行可能な形でコピーしておく。 |
| **ルート（おおもとのディレクトリ）** | リファクタ**後**のコード。`frontend/` `backend/` `db/` `docker-compose.yml` 等をここに置き、ここを本番・開発の基準とする。 |

- **改編内容（リファクタ後のコード）はルートに格納**するため、普段の編集・デプロイはルートの `frontend/` `backend/` `db/` に対して行う。
- `pre/` は「以前の状態」のスナップショットとして残し、必要なら `pre/` 内で `npm install` して旧版を起動できる。

### 1.2 リファクタ着手前の手順

1. **pre/ を作成し、現在のコードをコピーする**  
   - スクリプト `scripts/backup-to-pre.sh` を実行する（後述）。  
   - または手動で `frontend/` `backend/` `db/` と必要なファイルを `pre/` にコピーする。
2. **ルートのコードをリファクタする**  
   - ルートの `frontend/` `backend/` `db/` を編集する。  
   - リファクタ後のコードはすべてルートに格納された状態になる。

### 1.3 リファクタ後のツリーイメージ

```
doll_roulette/                    ← おおもとのディレクトリ（改編内容＝リファクタ後コード）
├── pre/                          ← リファクタ前のコード（参照用）
│   ├── frontend/
│   ├── backend/
│   ├── db/
│   ├── docker-compose.yml
│   ├── .env.example
│   ├── scripts/
│   └── docs/
├── frontend/                     ← リファクタ後
├── backend/
├── db/
├── docker-compose.yml
├── docs/                         ← 改編内容の説明・計画書もここ
├── scripts/
│   └── backup-to-pre.sh
└── ...
```

## 2. pre/ へのコピー方法

### 2.1 スクリプトで一括コピー（推奨）

```bash
# プロジェクトルートで実行
bash scripts/backup-to-pre.sh
```

- **コピーするもの**: `frontend/` `backend/` `db/` `docker-compose.yml` `.env.example` `.dockerignore` `.cursorrules` `README.md` `概要メモ.md` `scripts/` `docs/`
- **コピーしないもの**: `node_modules/` `.env` `dist/` `.git/` `backend/uploads/`（データは別途引継ぎ）

初回は `pre/` が無い状態で実行すると `pre/` が作成され、上記がコピーされる。2回目以降は上書きされる。
- **要 rsync**: WSL/Ubuntu では通常同梱。未導入の場合は `sudo apt install rsync` でインストール。

### 2.2 手動でコピーする場合

- `pre/` を作成し、以下をコピーする。  
  - `frontend/`（`node_modules` を除く）  
  - `backend/`（`node_modules` `uploads` を除く）  
  - `db/`  
  - `docker-compose.yml` `.env.example` `.dockerignore` `.cursorrules` `README.md` `概要メモ.md`  
  - `scripts/` `docs/`
- `pre/` 内で旧版を動かす場合は、`pre/frontend` と `pre/backend` でそれぞれ `npm install` する。

## 3. データの引継ぎ（可能です）

リファクタ後も**現在のデータ（DB・画像）をそのまま使う**ことが可能。スキーマが同じであれば、以下の手順で引継ぎできる。

### 3.1 データベース（PostgreSQL）の引継ぎ

- **前提**: リファクタ後も `db/init/01_schema.sql` と同じテーブル・カラムを維持する（リファクタリング計画書の方針）。
- **手順**:
  1. **リファクタ前の環境**で DB をダンプする。  
     ```bash
     docker compose exec db pg_dump -U doll_roulette doll_roulette > backup.sql
     ```
     （`POSTGRES_USER` / `POSTGRES_DB` が違う場合はその値に合わせる。）
  2. **リファクタ後の環境**で PostgreSQL を起動し、空の DB を用意する（`docker compose up -d db` で初回に `01_schema.sql` が実行される）。
  3. ダンプをリストアする。  
     ```bash
     docker compose exec -T db psql -U doll_roulette doll_roulette < backup.sql
     ```
- 既存の `postgres_data` ボリュームをそのままリファクタ後の `docker-compose` で使い回すことも可能。その場合は **DB のバックアップだけ別途取得しておく**ことを推奨。

### 3.2 画像（uploads）の引継ぎ

- **現状**: 画像は `backend/uploads/`（Docker の `uploads_data` ボリューム）に保存され、DB の `image_url` は `/uploads/...` のようなパス。
- **リファクタ後もローカル保存を続ける場合**:
  - 同じ Docker の `uploads_data` ボリュームを、リファクタ後の `docker-compose.yml` でもそのまま使えば、**追加のコピーは不要**で引継ぎ完了。
  - 別環境に移す場合は、`backend/uploads/`（またはボリュームのマウント先）の中身をそのまま新しい環境の `backend/uploads/` にコピーする。DB の `image_url` は `/uploads/...` のままなので、パスは変えなくてよい。
- **リファクタでストレージを抽象化し、保存先を Object Storage などに変える場合**:
  - 移行手順では「既存の `uploads` 内ファイルを新しい保存先にアップロードし、DB の `image_url` を新しい URL に更新する」スクリプトや手順を別途用意する（クラウド移設用リファクタの範囲）。

### 3.3 引継ぎの流れ（まとめ）

| データ | 引継ぎ方法 |
|--------|------------|
| **DB** | `pg_dump` → リファクタ後環境で `psql` にリストア。または既存 `postgres_data` をそのまま利用。 |
| **画像** | 同じ `uploads_data` ボリュームをリファクタ後も使う、または `uploads/` の中身を新環境にコピー。 |

- スキーマとパスを変えなければ、**現在のデータをそのまま引継ぎ可能**。

---

## 4. 注意点

- **pre/** は参照用のため、`pre/` 内のコードを本番デプロイしない。本番・開発は常に**ルート**のコードを使う。
- **.env** はコピーしない。`pre/` で旧版を動かす場合は `pre/.env.example` をコピーして `pre/.env` を作成する。
- データ引継ぎの前に、**必ず DB のダンプと uploads のバックアップ**を取っておく。
