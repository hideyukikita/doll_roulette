# かぞくたちルーレット リファクタリング計画書

**作成日**: 2026年2月  
**目的**: アプリの設計・構成の見直しを**クラウド移設とは別**に計画する。DB設計・ディレクトリ配置・画像の保存方法などを、保守しやすく拡張しやすい形に整える。

**位置づけ**:
- **クラウド移設**は [移設計画書_OracleCloudおよび代替案.md](./移設計画書_OracleCloudおよび代替案.md) で扱い、現状のアプリのまま載せる想定。
- 本計画は**リファクタリング単体**の計画。実施タイミングは移設の前後どちらでもよい。
- 移設後に「クラウド移設用のリファクタリング」（例: 画像を Object Storage に移す）を行う場合は、本計画の内容をベースに、クラウド向けの変更を追加する形で行う。

---

## 0. ディレクトリ構成とデータ引継ぎ

- **pre/ にリファクタ前のコードを退避し、改編後（リファクタ後）のコードはおおもとのディレクトリ（ルート）に格納する**構成が可能。
- リファクタ着手前に `scripts/backup-to-pre.sh` を実行すると、現在の `frontend/` `backend/` `db/` 等を `pre/` にコピーできる。その後はルートのコードだけを編集する。
- **現在のデータ（DB・画像）の引継ぎは可能**。スキーマを維持すれば `pg_dump`/`psql` で DB を移行でき、画像は同じ `uploads_data` ボリュームを使うか、`uploads/` をコピーすればよい。
- 手順の詳細は **[リファクタリング_ディレクトリ構成とデータ引継ぎ.md](./リファクタリング_ディレクトリ構成とデータ引継ぎ.md)** を参照。

## 1. 現状の整理

| 項目 | 現状 | 課題（リファクタの観点） |
|------|------|---------------------------|
| **画像保存** | バックエンドの `/uploads`（ローカル＋Docker ボリューム）。multer でディスク保存。 | 保存先がコードに直書き。クラウド・複数インスタンス対応時に変更が分散する。 |
| **DB** | PostgreSQL、スキーマは `db/init/*.sql`。追加設計を重ねた形。 | 運用上は問題なし。必要に応じてインデックス・型の見直しやドキュメント整理。 |
| **ディレクトリ** | frontend / backend / db / docs / scripts | 大きな問題はなし。設定・ストレージの責務を config に寄せると見通しが良くなる。 |
| **設定** | ルート `.env` を Compose で注入 | 本番では環境変数のみにしたい。NODE_ENV による分岐があると運用しやすい。 |

## 2. DB 設計の見直し

### 2.1 方針

- **テーブル構成は現状のまま**でよい（dolls, doll_images, histories, outings, outing_dolls, outing_images）。
- リファクタで行うこと:
  - **接続情報**: すでに環境変数化済み。本番では secrets 等で注入する運用を前提にドキュメント化。
  - **初期化**: `db/init/01_schema.sql` を新規構築時の唯一の入口として明記。02〜05 は既存 DB 用のマイグレーション用であることを README や docs に記載。
- 将来マネージド DB（Render Postgres 等）を使う場合も、スキーマはそのまま流用し、接続文字列の切り替えのみで対応可能。

### 2.2 任意で検討できること

- インデックスの見直し（利用クエリに合わせた追加・削除）。
- 日時型のタイムゾーン表記の統一（すでに `TIMESTAMP WITH TIME ZONE` 使用のため、大きな変更は不要）。

## 3. ディレクトリ・設定の整理

### 3.1 方針

- **frontend / backend / db** の大構成は維持。
- **設定の集約**:
  - 本番用は **環境変数のみ**で賄い、`.env` をリポジトリに含めないことをルール化。
  - `backend/config/` に、`NODE_ENV` で分岐する設定（例: ログレベル、CORS のオリジン制限）をまとめると、本番・開発の切り替えが明確になる。
- **シークレット**: パスワード類は環境変数または実行環境のシークレット機能で渡す方針をドキュメントに残す。

### 3.2 変更イメージ（最小）

```
backend/
  src/
    config/
      db.ts         # 既存
      app.ts 等     # 必要に応じて CORS・ログ等を NODE_ENV で分岐
```

- 既存の `config/db.ts` はそのまま。必要なら `config/index.ts` でまとめて export する程度。

## 4. 画像保存の見直し

### 4.1 課題

- 保存先が「ローカル `/uploads`」に固定されており、クラウドやスケールを考えると選択肢を持ちたい。
- リファクタの目的は**保存先を差し替え可能にすること**（ローカル / Object Storage / S3 互換など）。

### 4.2 方針: ストレージ抽象レイヤー

- **ストレージ層を 1 箇所にまとめる**。呼び出し側（routes）は「ファイルを保存する」「URL を返す」「削除する」だけを利用する。
- 実装として:
  - **ローカル**: 現状の `uploads` ディレクトリ＋multer の diskStorage。
  - **クラウド（移設用リファクタで追加）**: OCI Object Storage や S3 互換。multer の memoryStorage で受け取り、SDK でアップロード。

### 4.3 実装イメージ

| 項目 | 内容 |
|------|------|
| **新規** | `backend/src/config/storage.ts` または `backend/src/services/storageService.ts` のようなモジュールを用意。 |
| **インターフェース** | `upload(buffer, path)`, `getPublicUrl(path)`, `remove(path)` のような API に統一。 |
| **環境による切り替え** | `STORAGE_TYPE=local` のときは現状のディスク保存、`STORAGE_TYPE=oci` などで Object Storage を選択（クラウド移設用リファクタで実装）。 |
| **routes** | dolls / outings の画像アップロード・削除は、このストレージ層を経由するだけにし、`/uploads` や OCI の詳細を直接書かない。 |

### 4.4 保存先の選択肢（参考）

| 方式 | 内容 | いつ使うか |
|------|------|------------|
| **ローカル（現状）** | `/uploads` + Docker ボリューム | 開発・現状の移設のまま運用 |
| **OCI Object Storage** | Always Free 20 GB。S3 互換 API。 | クラウド移設用リファクタで本番を OCI に載せる場合 |
| **S3 互換（他サービス）** | Cloudflare R2 等 | クラウド移設先が OCI 以外の場合の選択肢 |

- **リファクタリング単体**では「ローカル＋抽象レイヤー導入」まで行い、**クラウド移設用のリファクタ**で OCI Object Storage（または他）の実装を追加する形にすると、役割が分かりやすい。

## 5. 移設用リファクタリングとの関係

- **通常のリファクタリング**（本計画）: DB・ディレクトリ・**画像の抽象レイヤー化**まで。保存先はローカルのままでもよい。
- **クラウド移設用のリファクタリング**（移設のタイミングで実施）:
  - 上記のストレージ層のうえに、OCI Object Storage（または他）の実装を追加。
  - 本番の環境変数で `STORAGE_TYPE=oci` とし、`image_url` を Object Storage の URL にする。
  - 移設計画書の「現状のまま移設」ではここまでやらない想定。移設後に「せっかくだから Object Storage にしよう」とする場合に実施。

---

## 6. 実施順序の提案

1. **設定の整理**（backend の NODE_ENV 分岐・CORS 等）— 影響範囲が小さい。
2. **ストレージ抽象レイヤーの導入**（保存・取得・削除を interface 化し、実装はローカルのみ）— 既存動作を変えずにリファクタ。
3. **DB 周りのドキュメント整備**（01_schema の位置づけ、02〜05 の用途を明記）。
4. （移設後に）**クラウド移設用リファクタ**で Object Storage 実装を追加。
