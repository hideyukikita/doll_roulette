# リファクタリング時のディレクトリ構成とデータ引継ぎ

**目的**: リファクタ前のコードを `pre/` に退避し、**改編後のコードはおおもとのディレクトリ（ルート）に格納**する構成にする。あわせて既存データ（DB・画像）の引継ぎ方法を記載する。

---

## 1. ディレクトリ構成（可能です）

### 1.1 方針

| 場所 | 内容 |
|------|------|
| **pre/** | リファクタ**前**のコード一式（バックアップ・参照用）。実行可能な形でコピーしておく。 |
| **ルート（おおもとのディレクトリ）** | リファクタ**後**のコード。`frontend/` `backend/` `db/` `docker-compose.yml` 等をここに置き、ここを本番・開発の基準とする。 |

- **改編内容（リファクタ後のコード）はルートに格納**するため、普段の編集・デプロイはルートの `frontend/` `backend/` `db/` に対して行う。
- `pre/` は「以前の状態」のスナップショットとして残し、必要なら `pre/` 内で `npm install` して旧版を起動できる。

### 1.2 リファクタ着手前の手順

1. **pre/ を作成し、現在のコードをコピーする**  
   - スクリプト `scripts/backup-to-pre.sh` を実行する（後述）。  
   - または手動で `frontend/` `backend/` `db/` と必要なファイルを `pre/` にコピーする。
2. **ルートのコードをリファクタする**  
   - ルートの `frontend/` `backend/` `db/` を編集する。  
   - リファクタ後のコードはすべてルートに格納された状態になる。

### 1.3 リファクタ後のツリーイメージ

```
doll_roulette/                    ← おおもとのディレクトリ（改編内容＝リファクタ後コード）
├── pre/                          ← リファクタ前のコード（参照用）
│   ├── frontend/
│   ├── backend/
│   ├── db/
│   ├── docker-compose.yml
│   ├── .env.example
│   ├── scripts/
│   └── docs/
├── frontend/                     ← リファクタ後
├── backend/
├── db/
├── docker-compose.yml
├── docs/                         ← 改編内容の説明・計画書もここ
├── scripts/
│   └── backup-to-pre.sh
└── ...
```

## 2. pre/ へのコピー方法

### 2.1 スクリプトで一括コピー（推奨）

```bash
# プロジェクトルートで実行
bash scripts/backup-to-pre.sh
```

- **コピーするもの**: `frontend/` `backend/` `db/` `docker-compose.yml` `.env.example` `.dockerignore` `.cursorrules` `README.md` `概要メモ.md` `scripts/` `docs/`
- **コピーしないもの**: `node_modules/` `.env` `dist/` `.git/` `backend/uploads/`（データは別途引継ぎ）

初回は `pre/` が無い状態で実行すると `pre/` が作成され、上記がコピーされる。2回目以降は上書きされる。
- **要 rsync**: WSL/Ubuntu では通常同梱。未導入の場合は `sudo apt install rsync` でインストール。

### 2.2 手動でコピーする場合

- `pre/` を作成し、以下をコピーする。  
  - `frontend/`（`node_modules` を除く）  
  - `backend/`（`node_modules` `uploads` を除く）  
  - `db/`  
  - `docker-compose.yml` `.env.example` `.dockerignore` `.cursorrules` `README.md` `概要メモ.md`  
  - `scripts/` `docs/`
- `pre/` 内で旧版を動かす場合は、`pre/frontend` と `pre/backend` でそれぞれ `npm install` する。

## 3. データの引継ぎ（可能です）

リファクタ後は **DB スキーマが変更**されています（`dolls.image_url` / `outings.image_url` を廃止し、画像は `doll_images` / `outing_images` のみ）。既存データはマイグレーションで引継ぎ可能です。

### 3.1 新規構築の場合

- `docker compose up` で DB を起動すると、`db/init/01_schema.sql` が実行され、**新スキーマ**（画像は *_images のみ）で初期化されます。追加作業は不要です。

### 3.2 既存 DB からリファクタ後へ移行する場合

- **手順**:
  1. **必ずバックアップを取得**  
     ```bash
     docker compose exec db pg_dump -U doll_roulette doll_roulette > backup.sql
     ```
  2. **マイグレーションを実行**（既存の `postgres_data` をそのまま使う場合）  
     ```bash
     cat db/migrations/001_drop_legacy_image_urls.sql | docker compose exec -T db psql -U doll_roulette doll_roulette -f -
     ```
     または、`001_drop_legacy_image_urls.sql` の内容を手動で実行する。  
     - `dolls.image_url` を `doll_images` に移行してからカラム削除  
     - `outings.image_url` を `outing_images` に移行してからカラム削除  
  3. リファクタ後のバックエンドを起動する。
- **新規インストールではなく既存 DB を流用する場合**は、初回のみ上記マイグレーションを実行すれば、**現在のデータをそのまま利用可能**です。

### 3.3 画像（uploads）の引継ぎ

- マイグレーションでは **DB に保存されている画像パス**（例: `/uploads/xxx.jpg`）をそのまま `doll_images` / `outing_images` にコピーするため、**ファイルの移動は不要**です。
- 同じ Docker の `uploads_data` ボリュームをリファクタ後もそのままマウントすれば、既存の画像ファイルはそのまま参照されます。
- リファクタ後に新規アップロードする画像は `uploads/dolls/{id}/` や `uploads/outings/{id}/` に保存されます。既存ファイルは従来のパスのままです。

### 3.4 引継ぎの流れ（まとめ）

| 状況 | 手順 |
|------|------|
| **新規構築** | `01_schema.sql` のみ実行（Docker 起動時で完了）。 |
| **既存 DB を流用** | バックアップ取得 → `db/migrations/001_drop_legacy_image_urls.sql` を実行 → リファクタ後アプリを起動。 |
| **画像** | `uploads_data` ボリュームをそのまま使う。新規アップロード分は新しいディレクトリ構成で保存。 |

---

## 4. 注意点

- **pre/** は参照用のため、`pre/` 内のコードを本番デプロイしない。本番・開発は常に**ルート**のコードを使う。
- **.env** はコピーしない。`pre/` で旧版を動かす場合は `pre/.env.example` をコピーして `pre/.env` を作成する。
- データ引継ぎの前に、**必ず DB のダンプと uploads のバックアップ**を取っておく。
