# パブリック公開時のセキュリティ

かぞくたちルーレットをインターネットに公開する際の「**いま何をしているか**」と「**検討すべきこと**」をまとめます。

---

## 1. いま追加している対策（実装済み）

| 対策 | 内容 | 役割 |
|------|------|------|
| **CORS のオリジン制限** | 本番で `ALLOWED_ORIGIN` を設定すると、そのオリジン（例: `https://your-domain.com`）からのリクエストだけ API を許可する。 | 第三者のサイトからあなたの API を勝手に呼ばれないようにする。 |
| **helmet** | HTTP レスポンスにセキュリティ用ヘッダーを付与（`X-Content-Type-Options: nosniff` など）。 | ブラウザのクロスサイトスクリプティングや MIME スニッフィングなどのリスクを抑える。 |
| **レート制限** | 同一 IP あたり 1 分間に 100 リクエストまで。超えると 429 を返す。 |  DoS やスクレイピングのやりすぎをある程度抑える。 |
| **入室用パスワード** | `.env` の `APP_PASSWORD` を設定すると、最初にパスワード入力画面を表示。正しいパスワードで Cookie（7日間有効）を発行し、以降は認証済みとして利用可能。未設定なら認証なし。 | 家族だけがアクセスできるようにする簡易ゲート。 |

- 開発時（`NODE_ENV=development`）は CORS は緩く（リフレクタ）、helmet とレート制限は**無効**です。
- パスワードは **APP_PASSWORD** に設定。設定しない場合は従来どおり認証なしで利用できます。
- 本番では `.env` で `NODE_ENV=production` と `ALLOWED_ORIGIN` を設定することが前提です。

## 2. もともとある対策

| 項目 | 内容 |
|------|------|
| **画像の MIME 制限** | `image/jpeg`, `image/png`, `image/gif`, `image/webp` のみアップロード許可（`storageConfig.allowedMimeTypes`）。 |
| **DB クエリ** | `pg` のパラメータ化クエリ使用のため、SQL インジェクションは回避されている想定。 |
| **秘密情報** | DB パスワードなどは環境変数（`.env`）で渡し、リポジトリに含めない運用。 |

## 3. パブリックだからこそ検討したいこと

### 3.1 認証（入室用パスワードは実装済み）

- **現状**: `.env` に **APP_PASSWORD** を設定すると、最初にパスワード入力画面が表示される。正しいパスワードで Cookie（7日間有効）が発行され、以降は API・画像とも利用可能。**未設定の場合は従来どおり認証なし**。
- **注意**: パスワードは 1 つだけ（「入室」のゲート）。ユーザーごとのログインや権限の切り分けはない。家族で 1 パスワードを共有する想定。
- **さらに厳しくする場合**: Nginx のベーシック認証を重ねる、または将来ユーザーごとのログイン（JWT 等）を検討する。

### 3.2 HTTPS の利用（強く推奨）

- **現状**: 手順書では Nginx + Let's Encrypt（certbot）で HTTPS 化を案内している。
- **推奨**: パブリック公開する場合は **必ず HTTPS** にすること。通信内容や Cookie（将来つける場合）の盗聴・改ざんを防ぐ。

### 3.3 画像の直リンク（/uploads/）の扱い

- **現状**: `/uploads/` は**認証済み（Cookie あり）のときだけ**配信。パスワード入室後のみ画像にアクセス可能。

### 3.4 レート制限の値

- **現状**: 100 リクエスト/分/IP。
- **検討**: 利用人数や使い方に応じて `max` を変更可能。厳しめにすれば負荷・悪用を抑えやすいが、正当な利用で弾かれないようにする。

### 3.5 ログ・監視

- **現状**: アプリ側のアクセスログ・エラーログの仕組みは最小限。
- **検討**: Nginx のアクセスログ、バックエンドのエラーログをどこに出すか・どう見るかを決めておくと、不審なアクセスや障害の切り分けがしやすい。

## 4. パブリック公開として問題ないか

**家族向け・URL を知っている人だけ**の前提であれば、次の条件を満たせば**一般的なパブリック公開として許容できる水準**です。

| 必須 | 内容 |
|------|------|
| ✅ | **APP_PASSWORD を設定** … 入室ゲートで第三者を遮断。 |
| ✅ | **HTTPS で運用** … Nginx + Let's Encrypt。Cookie と通信の盗聴・改ざんを防ぐ。 |
| ✅ | **ALLOWED_ORIGIN を本番 URL に設定** … CORS で他サイトからの API 利用を防ぐ。 |
| ✅ | **POSTGRES_PASSWORD を推測されにくい値に** … DB を守る。 |

このうえで、CORS・helmet・レート制限・MIME 制限・パスワード認証がそろっていれば、**「知らない人が偶然アクセスして中身を見る」リスクはかなり下がります**。  
一方で、**銀行や医療のような高機密サイトのレベル**ではありません（単一パスワード共有、ユーザーごとの権限なし、監査ログは最小限）。家族の写真・ルーレット用途なら、上記で十分な場合がほとんどです。

---

## 5. まとめ

- **いまやっていること**: CORS 制限・helmet・レート制限・入室用パスワードで、「第三者のサイトからの利用」「よくあるヘッダー攻撃」「過度なリクエスト」「入室していない人」を抑えている。
- **パブリックにするなら**: **HTTPS** と **APP_PASSWORD** を必ず入れ、**ALLOWED_ORIGIN** を本番 URL に合わせる。
